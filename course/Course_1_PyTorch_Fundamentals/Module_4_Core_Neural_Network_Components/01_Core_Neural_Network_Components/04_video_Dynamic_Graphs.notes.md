## Отправная точка: обученная CNN — это просто стек слоёв

Только что была обучена первая convolutional neural network для приложения Botanical Garden. Но если присмотреться, структура получилась полностью линейной: данные проходят строго по прямой — три блока (свёртка, ReLU, pooling), затем flatten и ещё несколько слоёв перед выдачей предсказания.

Это неплохое начало, но пока это просто стек слоёв. Он выглядит однотипным и не показывает, что делает PyTorch особенным. В PyTorch пользователь не заперт в этой жёсткой структуре модели — это достигается за счёт **dynamic computation graph (динамического вычислительного графа)**, который строится по мере выполнения модели, шаг за шагом.

Как упоминалось ещё в модуле 1, старые фреймворки работали иначе: нужно было заранее, до прохождения каких-либо данных, определить вычислительный граф целиком.

## Что такое computation graph

Рассмотрим модель, определённую через `nn.Sequential`:

```python
model = nn.Sequential(
    nn.Conv2d(3, 32, 3),
    nn.ReLU(),
    nn.Conv2d(32, 64, 3),
    nn.ReLU(),
    nn.Flatten(),
    nn.Linear(64 * 26 * 26, 10)
)
```

Модель прогоняет данные через каждый слой по порядку, как и следовало ожидать. Каждый слой преобразует вход и передаёт его дальше. Это просто, читаемо и эффективно для прямолинейных архитектур.

Но здесь есть подвох: `Sequential` жёстко фиксирует структуру. Он **не поддерживает циклы, условные конструкции или другую ветвящуюся логику**. По сути, такой код не так уж сильно отличается от того, как строились модели в старых фреймворках со статическими графами.

Когда пишется такой sequential-блок, фактически задаётся конкретное математическое уравнение:

- `Conv2d` может описывать тысячи умножений и сложений;
- `ReLU` обнуляет все отрицательные значения;
- при соединении в цепочку получается одно большое уравнение.

Представим, что нужно было бы расписывать это уравнение целиком на каждом отдельном вычислении, шаг за шагом: умножить это на то, добавить результат к этому, обнулить отрицательные значения, снова умножить, добавить bias — и так далее бесчисленное количество раз. Такая пошаговая раскладка вычислений и есть **computation graph**.

Каждая применяемая операция записывается как часть этого графа. Зачем? Потому что во время обучения всем фреймворкам глубокого обучения нужно пройти по графу в обратном направлении, используя **chain rule** (цепное правило) из математического анализа — именно так вычисляется, как скорректировать каждый параметр.

## Старые фреймворки vs PyTorch

Старые фреймворки обрабатывали это иначе, чем PyTorch сейчас: весь граф нужно было определить заранее — каждую операцию, каждую связь — прежде чем что-либо могло запуститься. После определения структура фиксировалась.

Когда в PyTorch используется `nn.Sequential`, работа идёт с похожими ограничениями:

- всё выполняется в фиксированном порядке;
- нельзя напечатать промежуточные значения для отладки;
- нет условных конструкций;
- нет циклов;
- каждый вход проходит один и тот же путь без исключений.

Именно поэтому `Sequential` немного похож на программирование со статическим графом: пользователь снова оказывается привязан к фиксированному уравнению без гибкости.

### Почему вообще так работали раньше

Может возникнуть вопрос: зачем вообще так делать? Оказывается, есть реальные преимущества, когда фреймворк заранее знает весь вычислительный граф — он может оптимизировать его по скорости и по эффективности использования памяти. Но за это приходится платить гибкостью, потому что описывается фиксированное уравнение: нет возможности что-то подправить по ходу дела или исследовать неожиданные идеи.

Именно это PyTorch решил изменить.

## Пример: разная логика для разных входов

Представим, что нужно построить CNN для приложения ботанического сада, но теперь модель должна обрабатывать цветы иначе, чем бабочек. В PyTorch такую логику можно написать прямо внутри метода `forward`:

```python
def forward(self, x):
    if self.is_flower(x):
        return self.flower_layers(x)
    else:
        return self.butterfly_layers(x)
```

В старых фреймворках со статическими графами такой контроль был очень труден. Да, условные конструкции были доступны, но только за счёт построения заранее всех возможных путей выполнения.

PyTorch устроен иначе: `if`-конструкция не просто управляет логикой — она формирует сам граф. Каждый раз, когда выполняется `forward`, PyTorch записывает в точности, что происходит: каждое умножение, сложение, слой и ветвление. В результате получается индивидуальный computation graph, построенный на лету, на основе того пути, который прошли конкретные данные. Этот граф используется для backpropagation, чтобы обновить параметры, а затем граф отбрасывается. При следующем запуске `forward` PyTorch начинает с нуля, строя новый граф под этот конкретный запуск, даже если он пойдёт по совершенно другому пути.

Это и есть ключевое отличие: статические фреймворки заставляют мыслить как компилятор, а PyTorch позволяет мыслить как программист на Python — писать логику, ветвиться, адаптироваться на лету.

## Откуда берётся эта гибкость

Гибкость возникает из использования `nn.Module` вместо `nn.Sequential`, где:

- `__init__` определяет модель (архитектуру);
- `forward` задаёт поток динамического графа.

Такие динамические графы имеют небольшую плату за производительность, но для исследователей и разработчиков эта гибкость означает более быструю итерацию, более лёгкую отладку и более выразительные модели.

## Это не просто красивая идея — реальные проблемы, которые она решает

- **Статические графы часто требуют, чтобы все входы имели одинаковую форму.** Но что делать, если данные — это предложения, где одни состоят из 3 слов, а другие, очень длинные, — из 50? В PyTorch это просто работает.
- **Отладка в середине вычисления.** В статических фреймворках для этого приходилось переключаться в специальный режим отладки — прервать поток выполнения было нельзя. В PyTorch это просто Python: если нужно разобраться с проблемой, достаточно добавить `print`.
- **Адаптивные модели.** Можно строить модели, которые подстраиваются под вход — например, запускать более простую модель для простых случаев и более сложную для сложных. Модель становится "умной" относительно собственных вычислений.

Это не какие-то редкие крайние случаи — именно так устроен современный AI. В PyTorch всё это возможно просто за счёт написания обычного Python-кода.
