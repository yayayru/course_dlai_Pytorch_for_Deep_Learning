## Контекст

В прошлом видео было показано, как ранние попытки ботанического сада создать приложение для идентификации цветов провалились из-за плохой работы с данными. Теперь настало время решить первую крупную проблему — **доступ к данным (data access)**. Если данные нельзя надёжно загрузить, ничего остальное не имеет значения. Показано, что идёт не так с "грязными" датасетами вроде Oxford Flowers, и как это исправить с помощью класса `Dataset` из PyTorch.

## Скачивание датасета

Функция скачивания предоставлена заранее (детали разбираются в лабораторной работе), но вкратце — она загружает и файлы изображений, и метки:

```python
def download_dataset():
    """Download the Oxford 102 Flowers dataset"""
    # URLs for the dataset
    image_url = "https://www.robots.ox.ac.uk/~vgg/data/flowers/102/102flowers.tgz"
    labels_url = "https://www.robots.ox.ac.uk/~vgg/data/flowers/102/imagelabels.mat"

    # Create directory
    os.makedirs("flower_data", exist_ok=True)
```

После скачивания: свыше 8000 изображений (8189), все с обобщёнными именами вроде `image0001.jpg`. Организации по типу цветка нет — это просто плоский (flat) список пронумерованных файлов. Метки хранятся отдельно, в файле `.mat` — бинарном формате, используемом MATLAB. Он сопоставляет каждое изображение с категорией цветка.

Таким образом, изображения находятся в одном месте, а метки — в другом месте и в совершенно другом формате. Нужен способ надёжно и систематично их связать.

## Зачем нужен собственный класс Dataset

В предыдущих модулях данные загружались с помощью готовых датасетов вроде MNIST — он уже "знал", как находить изображения и сопоставлять их с правильными метками. Oxford Flowers не поставляется в таком готовом виде, поэтому нужно показать PyTorch, как работать с этим датасетом, построив собственный класс `Dataset`.

Пользовательский класс `Dataset` в PyTorch должен отвечать на три вопроса:

1. `__init__` — как настроить датасет и где находятся данные?
2. `__len__` — сколько всего образцов?
3. `__getitem__` — что вернуть, когда запрашивают конкретный образец (например, изображение №42)?

Эти три метода — всё, что нужно PyTorch для работы с любым форматом данных.

```python
class OxfordFlowersDataset(Dataset):
    # Setup: where to find images and labels
    def __init__(self):
        ...

    # How many total samples
    def __len__(self):
        ...

    # How to get image and label number 'idx'
    def __getitem__(self, idx):
        ...
```

## Метод `__init__`

`__init__` — это метод настройки. Здесь указывается, где найти всё необходимое, и загружается любая информация, которая понадобится позже.

```python
class OxfordFlowersDataset(Dataset):
    def __init__(self, root_dir):
        self.root_dir = root_dir
        self.img_dir = os.path.join(root_dir, 'jpg')

        # Load Matlab labels
        labels_mat = scipy.io.loadmat(os.path.join(root_dir, 'imagelabels.mat'))

        self.labels = labels_mat['labels'][0] - 1
```

Датасету требуется определённая настройка: обработка путей к файлам, чтение MATLAB-файла с помощью **SciPy** (`scipy.io.loadmat`), а также исправление индексации меток. Именно это делает пример реалистичным. В результате получается доступ ко всем путям к изображениям и соответствующим меткам.

### Что внутри массива меток

- Всего **8189 меток**, по одной на изображение.
- Каждая метка — число от **1 до 102**, представляющее тип цветка.
- Первые 10 изображений имеют метку типа 1 — похоже, датасет организован по категориям (образцы одного класса идут подряд).
- Проверка `self.labels.min()` / `self.labels.max()` даёт **1** и **102** — то есть метки **не индексированы с нуля** (not zero-indexed).
- PyTorch ожидает метки с индексацией от 0. Есть 102 типа цветов, но вместо диапазона 1–102 нужен диапазон **0–101**. Это тот тип детали, которая может незаметно сломать обучение.
- Исправление: вычесть 1 из каждой метки — `self.labels = labels_mat['labels'][0] - 1`. После этого `min()` = 0, `max()` = 101.

### Ленивая загрузка (lazy loading)

Важно, что в `__init__` **не загружаются никакие изображения** — только настраивается информация, необходимая для их последующего поиска. Это называется **ленивой загрузкой (lazy loading)**, и это критически важно.

Антипаттерн — то, что делать **не следует**:

```python
class OxfordFlowersDataset(Dataset):
    self.all_images = []
    for i in range(8189):
        img = Image.open(f'image_{i:05d}.jpg')
        self.all_images.append(img)
```

Загрузка всех 8189 изображений сразу заняла бы гигабайты памяти — "4GB оперативной памяти испаряются мгновенно". Вместо этого сохраняются только пути и метки; фактическая загрузка изображений произойдёт позже, в `__getitem__`.

## Метод `__len__`

Простой метод — возвращает общее количество образцов в датасете. Так как на каждое изображение приходится одна метка, длина массива меток говорит PyTorch, сколько именно образцов ожидать. PyTorch использует это значение, чтобы правильно проходить по данным во время обучения.

```python
def __len__(self):
    return len(self.labels)  # 8,189 samples
```

## Метод `__getitem__`

Самый важный метод. Идея: PyTorch передаёт индекс, и задача метода — вернуть данные для этого индекса. Например: PyTorch говорит "дай мне образец номер 42", и в ответ возвращается 42-е изображение цветка и его метка (тип цветка, который оно представляет).

```python
from PIL import Image

def __getitem__(self, idx):
    # Build the image filename
    img_name = f'image_{idx:05d}.jpg'
    img_path = os.path.join(self.img_dir, img_name)

    # Load the image
    image = Image.open(img_path)
    label = self.labels[idx]

    return image, label
```

- `:05d` дополняет индекс нулями слева, чтобы соответствовать именам файлов (например, `image00042.jpg`).
- Для загрузки изображения используется **PIL (Pillow)** — библиотека для работы с изображениями в Python, через `Image.open`.
- Затем из массива меток берётся соответствующая метка.

Это контракт метода: определяется, как выглядит каждый образец, а PyTorch сам решает, как, когда и как часто вызывать этот метод.

## Проверка и исправление off-by-one ошибки

При первой попытке протестировать датасет возникла ошибка. Причина: файлы изображений названы `image0001`, `0002`, `0003` и т.д. — нумерация начинается с **1**, а не с 0. Когда запрашивается индекс 0, код пытается загрузить `image0000.jpg`, но такого файла не существует.

Исправление в `__getitem__` — добавление 1 к индексу при построении имени файла:

```python
from PIL import Image

def __getitem__(self, idx):
    # Build the filename
    img_name = f'image_{idx+1:05d}.jpg'  # Add 1 to filename
    img_path = os.path.join(self.img_dir, img_name)
    . . .
```

После исправления тест проходит успешно. Это классический пример того, почему датасет всегда нужно тестировать на раннем этапе: простая ошибка на единицу (off-by-one) могла бы незаметно сломать всё позже.

```python
class SomeDataset(Dataset):
    # Setup: where to find images and labels

        ...

        ...

    # How to get image and label number 'idx'
    def __getitem__(self, idx):
        ...
```

Построен пользовательский датасет, который систематически даёт доступ более чем к 8000 изображениям и меткам, не переполняя память.
